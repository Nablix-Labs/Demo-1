## 1. An unreadable canvas fails the whole submission (highest impact)

`POST /canvas/submit` answers:

```
503 ADAPTER_UNAVAILABLE
message: error=Content not found error_info={'id': 'image_no_content', 'message': 'Content not found'}
request_id: REQ7CF931F5   (also REQ2751FB50)
```

whenever the OCR provider finds nothing legible in the image.

### Why I am confident it is content, not the image

My first theory was transparency — the canvas exports a transparent PNG and a
provider that flattens transparent to black would see black-on-black. **That
theory was wrong**, and I tested it rather than reporting it. Then I tested
size. Also wrong. The full matrix:

| Image sent | Bytes | Result |
|---|---|---|
| Two zigzag scribbles, 2396×1800, transparent background | 126,982 | 503 `image_no_content` |
| The identical scribbles flattened onto opaque white | 126,554 | 503 `image_no_content` |
| Same scribbles, 400×301 | 6,446 | 503 `image_no_content` |
| Same scribbles, 800×601 | 20,030 | 503 `image_no_content` |
| Same scribbles, 1200×902 | 40,714 | 503 `image_no_content` |
| Same scribbles, 1600×1202 | 68,470 | 503 `image_no_content` |
| Same scribbles, 2000×1503 | 105,330 | 503 `image_no_content` |
| Blank white page, 2396×1800 | 119,462 | 503 `image_no_content` |
| **Legible "n + 4", 400×200** | (not recorded) | **200 `processed`** |
| **Legible "n + 4", 2396×1800** | 123,086 | **200 `processed`** |

Every other field in the body was held identical across all ten requests — only
`snapshot_data_url` and `turn_id` changed. So it is not size, not transparency,
not encoding, not payload shape. It is purely whether the image contains
readable content.

Two controls confirming the endpoint's own validation is working fine:

| Mutation | Result |
|---|---|
| `snapshot_data_url` removed | 422 `MISSING_FIELD` — correct |
| base64 sent without the `data:image/png;base64,` prefix | 422 `INVALID_VALUE` — correct |

### The ask

**"OCR read nothing" is a normal tutoring outcome, not an adapter outage.**

A student who taps Check with a doodle, a stray mark, a half-formed digit, or
an accidentally blank canvas currently gets a hard 5xx. That is not an edge
case — it is Phase 2 with a 13-year-old and a stylus.

It should come back as a **200** the tutor can respond to — something the
classifier can turn into "I couldn't quite read that, can you write it a bit
larger?" — rather than a 503 that fails the turn. If it genuinely has to stay
an error, please give it its own code (e.g. `CANVAS_NOT_LEGIBLE`, 422) so the
frontend can tell it apart from a real adapter outage.

### What the frontend does today

It degrades — the ink is kept, the toolbar re-enables, nothing freezes — and
the chat says:

> "The tutor service hit an error on its side. Nothing you did — try again in
> a moment."

Which is the right message for a real 503 and the wrong message here: the
student *did* do something, and trying again unchanged will fail again. I can
write better copy the moment there is a distinguishable code to key off. Until
then the frontend cannot tell the two apart, and I would rather not guess from
a message string.

## 2. `show_scaffold_panel: true` with nothing behind it

This is the answer to "scaffolding isn't appearing" (row 21). Live session
record, read just now:

```json
{
  "show_scaffold_panel":         true,
  "scaffold_id":                 null,
  "current_scaffold_step_id":    null,
  "scaffold_step_number":        1,
  "scaffold_total_steps":        0,
  "delivered_scaffold_step_ids": []
}
```

The flag says open the panel; there is no step to put in it.

The frontend renders nothing in this state, deliberately — `activeScaffold()`
in `lib/api.ts` returns null unless both `scaffold_step_text` and
`current_scaffold_step_id` are present, so a partial payload can never leave an
empty or stale panel on screen. That is the correct degradation and I am not
changing it: rendering "Step 1 of 0" with no content would be worse than
rendering nothing.

**Ask:** either send the step alongside the flag, or don't raise the flag.
Whichever is easier — the frontend is ready for the panel the moment
`scaffold_step_text` + `current_scaffold_step_id` arrive together.

## 3. `per_question_history` empty after 7 attempts (row 17)

Same live session:

```

hint_count:            2
canvas_submissions:    1

question_completed:    false
status:                "started"
```

This is exactly the precondition described in row 17 — "any session with zero
`per_question_history`, but the auto-transition to REVIEW doesn't check this,
which creates an un-endable session". I am not claiming the session is stuck;
I did not try to end it, because it is a shared dev session and I did not want
to destroy state you might want to inspect. But the state that row 17 warns
about is present right now on a session that has genuinely been worked through,
so it is worth confirming whether the REVIEW transition still skips the check.
