## 1. The blank page on topic transition — fixed

The Notion page had it right: three cascading causes, all of them ours. All
three are fixed. What follows is what I actually changed, because I did not
apply the fix plan as written and you should know why.

### Cause 1 — `notFound()` on a backend topic code

`getTopic` answers for the four mock curriculum ids (`algebra`, `number`,
`geometry`, `statistics`) and nothing else. Every real topic id is a curriculum
CODE from the Student Model. So the lookup missed on every live topic, both
clients answered the miss with `notFound()`, and with no `not-found.tsx` in the
tree Next unmounted everything inside `AppFrame` and left an empty div.

This was worse than the Notion page describes. It hit `/diagnostic/[topic]` too,
and `PHASE_0_DIAGNOSTIC` is the *default* `entry_phase` on a handoff — so it was
the first screen of every new topic, not just the orientation case.

New `lib/topicDisplay.ts` degrades instead of refusing:

1. the name the session sent (`sessionTopicTitle` — the orientation bundle, or
   `phase4_review.topic_info` at Review),
2. the curriculum title when the id happens to be a mock one,
3. the code itself.

**I did not fall back to the `'algebra'` fixture**, which is what the Notion plan
proposed. That would have put mock Algebra content, title and lesson list under
an unrelated backend topic — a wrong topic renders convincingly, which is worse
than one that renders awkwardly.

**And the last resort prints the code raw** — `ALG-ORI-02`, not "Alg Ori 02".
Prettying a code into a title invents a topic name in front of a student, which
is what QA row 42 records. In practice step 3 is nearly unreachable now that
`topic_info` ships: step 1 answers at orientation and at review.

Mock mode still requires its fixture and still calls `notFound()`. It has no
backend to name the topic, so there is genuinely nothing to render.

### Cause 2 — static export, still open, and I'd like your view

Unchanged and I have not guessed at it. `/app/orientation/ALG-ORI-02/index.html`
does not exist on disk, so nginx `try_files` falls through to `/app/index.html`
and serves the root lessons page. Verified live today.

**The reported bug is fixed regardless**, because the transition itself is a
client-side `router.push` — Next routes it in the browser with the bundle
already loaded and never requests that document. What is still wrong is a
refresh or a deep-link on a topic URL.

The Notion plan fixes this by hardcoding `['ALG-KS3-01', 'ALG-ORI-02', 'ALG-03',
'ALG-04']` into `generateStaticParams`. I have not done that. It is stale the
first time the curriculum gains a topic, and it fails silently and identically
to the bug it fixes, so nobody will connect the two.

The two honest options are a sentinel catch-all route plus an nginx `try_files`
line pointing at it, or moving the topic onto a query param
(`/orientation?topic=ALG-ORI-02`), which is one static file and works for any id
forever. The second is cleaner and changes every topic URL. Neither is a patch,
so I would rather agree on one than pick.

**Is there a bounded set of topic codes I could enumerate at build time?** If the
backend can expose the curriculum's codes on an endpoint, a build step could
generate the params honestly and this stops being a design question.

### Cause 3 — the finished session's phase outliving it

Confirmed exactly as described. `next_topic_handoff` pushes the student to the
next topic, but `currentPhase` is still the *previous* session's `REVIEW`, so
`usePhaseRouting` reads it as the new page mounts and pushes them straight back
to `/review`.

The handoff now clears it, and `routeForPhase('')` routes nowhere.

Clearing rather than setting it to the handoff's `entry_phase` is deliberate,
and it is your answer applied: the old session is over, the new one has not
reported yet, and the honest value for "what phase is this student in" is *not
yet known*. Guessing it from a pre-session field is the habit you asked me to
drop. The student stays where the handoff put them until `/session/start`
answers.

### Also: `app/not-found.tsx`

There was no not-found boundary anywhere in the tree, which is why all of this
produced a *blank* page rather than a bad one. There is one now. It is the floor,
not the fix — but the next unhandled id will be a readable screen with a way out.

## 3. Ask 3 — the rendering bug isn't there

This is the one place I have to disagree, and I checked carefully before writing
it because your diagnosis of the *backend* side was exactly right.

You wrote: *"Branch on that and ST015 stops getting a congratulatory summary on a
topic they got wrong."*

There is no congratulatory summary. Nothing in the Phase 4 screen branches on
`skipsReplay` to produce praise. When `tutor_replays` is empty the student sees:

- the journey rail, with their one attempt marked **"Needs review"**,
- the engine's own `strength_summary` / `development_summary` / `next_practice_focus`,
- `mastery_status` verbatim — **"Nearly mastered"** for ST015.

All authored by the engine, none of it asserted by the client. Verified live
today on the deployed build, not read off the source.

So `question_journey.some(row => row.evaluation !== "CORRECT")` would have
changed nothing on screen, and I have not added it — a branch whose two arms
render identically is a claim that they differ.

**Your underlying point was still right and I have acted on it.** The predicate
was *documented* as "§8.8: with no wrong answers the replay section is skipped",
which is false for precisely the reason you set out, and that comment is how the
congratulatory path you predicted would eventually get built on top of it. The
doc now says what it actually answers — "is there anything to replay", not "did
the student get everything right" — carries your canvas-path explanation and the
live ST015 shape, and states in as many words that nothing congratulatory may be
hung off it. The correct predicate is written there for whoever needs it.

Noted on `PARTIAL` never reaching Review. I've left the handling in place —
`evaluationOf` normalises unknown values to `WRONG`, so it costs nothing and is
the branch that cannot flatter — but I've stopped treating it as pending.

## 4. Routing off the session — agreed, and one residual

Understood and accepted: `/session/start` is authoritative, `last_journey_state`
is the pre-session snapshot, and the `PHASE_3` / `REVIEW` pairing is the intended
tested shape rather than drift. I've documented it as such.

In practice the deployed app already lands correctly: logging in as ST015 today
goes to `/review` and renders the Phase 4 screen, with one `POST /session/start`
and no page errors.

**The residual**, which I am flagging rather than fixing because it needs a
product answer: `landingRoute` still routes off `last_journey_state` *first*,
and the session correction arrives afterwards via `usePhaseRouting`. For ST015
the interim destination is `/practice`, which for an exhausted student is an
error state. On a fast connection it is invisible. On a slow one it is a broken
screen that then fixes itself.

Routing only off the session means holding the student somewhere while
`/session/start` runs — and that request can take **7+ seconds** when it enters
REVIEW, which you've confirmed is expected. So the real question is what they
look at for those seconds. A skeleton on a neutral screen is my instinct, but
that is Manjusha's call more than mine, so I have not built it.

Nothing for you here either way.
