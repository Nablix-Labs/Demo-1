## 1. `question_usage_id` is not on the session record — but recovery is told to compare it

**Contract, step 4:** "Compare identity before re-enabling Check. Session,
topic, `question_id` and `question_usage_id`."

**The field does not exist on the session record, on either side of the wire.**

```
$ grep -c question_usage_id app/models/session.py
0
```

It exists only on the Phase 4 and work-artifact models — `phase4_review.py:44`,
`work_artifact.py:21`, `topic_event_history.py:41`. So `GET /session` cannot
return it, and the client cannot compare it.

**What I did instead:** compared the three fields that do exist (session, topic,
`question_id`) and documented the gap in `lib/sessionRecovery.ts` rather than
inferring the fourth. Inferring it would be the client re-deciding question
identity, which is the exact failure the guard exists to prevent.

**Why it actually matters — one real case.** The three fields compare *equal*
when the same `question_id` is re-served as a **new usage**. That is precisely a
Guided repair return: `RESUME_SAME_INDEPENDENT_QUESTION` re-serves the same
question id, and the contract itself says `question_usage_id` is what
distinguishes the attempt (§"Returning from a Guided repair"). Today that path
arrives through `phase3Routing` rather than conflict recovery, so nothing is
broken — but the identity guard is one field short of the contract, and the
missing field is the one that separates a re-serve from a genuine match.

**Ask:** add `question_usage_id` to the session record so `GET /session` carries
it. One field; the client comparison is already written to take it.

## 3. Phase 4: "partially correct should also get a tutor review" is not implementable today

**Request:** Manjusha, 9 Sep — partially correct answers should also get a tutor
review in Phase 4.

**PARTIAL does not exist as a Phase 3 evaluation.** The vocabulary is binary
everywhere on the independent-practice path:

| Where | Values |
|---|---|
| `topic_event_history.py:43` — the attempt record Phase 4 reads | `CORRECT \| INCORRECT \| WRONG` |
| `phase4_review.py:10` — `Phase4Evaluation` | `INCORRECT \| WRONG` |
| `student_model_session.py:398` — events to Saravanan | `CORRECT_ATTEMPT \| INCORRECT_ATTEMPT` |
| `schemas.py:112` — canvas step evaluation | `CORRECT \| INCORRECT` |

`PARTIAL` appears only in `GuidedStudentState` (`guided_learning.py:12`) — that
is **Phase 2**, a different phase with a different classifier.

Replay selection then filters on wrongness:

```python
# app/services/phase4_replay_filter.py:29-33
return [
    attempt for attempt in attempts
    if attempt.phase == PHASE_3 and attempt.is_wrong
]

# app/models/topic_event_history.py:62-63
def is_wrong(self) -> bool:
    return self.evaluation in {"INCORRECT", "WRONG"}
```

**The frontend needs no change.** It is already agnostic and has been since the
Phase 4 build: `journeyRows` links a question to a replay via `review_item_id`,
explicitly *not* via evaluation (`lib/phase4Review.ts:88`); `skipsReplay` is
just "are there any replays" (`:114`); `Phase4Evaluation` in `lib/api.ts:1301`
already includes `PARTIAL`; and `ReviewRail` already renders the amber dot and
the "Partial" label. **The moment a PARTIAL attempt arrives carrying a
`review_item_id`, it gets a tutor review and a clickable rail row with zero
frontend edits.**

**Ask — four changes, three owners:**

1. **Product decision first:** what counts as "partially correct" in independent
   practice? There is no definition today.
2. **Classifier** must be able to mark a Phase 3 attempt `PARTIAL` — you / Sanya.
3. **`TopicAttemptRecord.evaluation` must accept it and the Student Model must
   emit it** — Saravanan, since the event vocabulary and topic event history are
   his.
4. **`filter_replay_attempts` must include it** — either add `PARTIAL` to
   `is_wrong` (which then misnames it) or give the filter a broader predicate.
   The second reads better: a partial answer is not a wrong one.

**Caveat on the screens Manjusha has seen.** The "Partial" row in the Phase 4
screenshots is my fixture (`lib/phase4Demo.ts:43`) inventing a state the
pipeline cannot currently produce. That is very likely what prompted the
request. I have left the fixture as-is pending the product decision above —
tell me if you would rather I drop it so the demo stops promising it.

## Two contract details that differ from the merged code

Not asks — just so the contract and the code agree next time someone reads
both. I built against the code.

- **`STALE_CANVAS_EVENTS` is not a 409.** The contract's table lists it under
  status 409. `canvas_service.py:333` returns `_stale_turn_response(session)` —
  a **200** with a `STALE_TURN` body. The contract's own footnote says as much
  ("a different envelope … no `error_code`"); only the status column disagrees.
  The client reads it off the reply rather than catching it.
- **`recommended_entry_phase: null` needed no frontend change.** It is only ever
  OR'd inside `reviewIsNext` (`lib/phase3.ts:192-201`) and never treated as
  "carry on with the recommendation", so the null case already falls through to
  `current_phase` as the contract requires.
