### "It works at the start, then breaks after some conversation" — Manjusha

That is the signature of the 409, and the logs show it literally: SESSION011 on
29 July had **three good turns and then died**; SESSION90188a33 today had good

question correctly — the advance to the next question is what poisons the
session. First question works, second question kills you. It presents as
"breaks after some conversation" because that is exactly what it is.

## The changes

### BACKEND — `cad2484` — ~~fix the session-killing 409~~ REVERTED in `72a995c` at Sanya's request

**Sanya's reasoning, which is fair:** clearing `student_model_event` on a bank
advance drops the session out of schema management, so Saravanan's Student
Model stops being authoritative for the rest of the phase. She owns this
service; SM continuity wins over my degrade-to-bank approach.

**What everyone must now know — the 409 session-killer is BACK.** Once a
correct answer advances the session onto a bank question (`ALG_1STEP_GP_*`),
the next answer 409s and the session is unrecoverable — the failure that
killed a lesson on 29 Jul and again on 31 Jul. Ask #1 in
`BACKEND-ASKS-2026-07-29.md` is open again and owns the real fix: serve
advances from the schema `question_set` instead of the bank, so the SM stays
authoritative AND the ids match. A `NOTE` comment at the advance site in
`interaction_service.py` marks this.

**To re-apply my interim fix if wanted:** `git revert 72a995c` — one command,
restores the whole thing (fix, message rewrite, regression test).

Original description, kept for the record:

`next_question_updates()` serves the next question from the Qdrant bank but
left the old Student Model event in place, so every schema lookup afterwards
409'd ("Student Model did not return metadata for ALG_1STEP_GP_F01/F02") and
the session was dead with no recovery.

The fix is one key in the advance dict: `student_model_event: None`. Every
schema reader already handles the None case by degrading to the plain
bank-question flow — the flow that worked before Schema 3.0 — and the next
phase start stores a fresh, consistent event. Also rewrites the 409 message,
which blamed the Student Model for an id the Tutor Backend assigned itself and
misdirected two debugging efforts.

Regression test included. Full backend suite: **313 passed**; the 6 failures
also fail on untouched `main` (env-dependent, verified by stashing).

**To revert:** `git revert cad2484` — restores previous behaviour exactly.

### BACKEND — `d4b417f` — /session/end 502'd for every session

Found by live-testing, not by a report: ae25494 (30 Jul) made session ids
durable (`SESSION{uuid hex}`) and updated the canonical validator, but
`SessionSummary` in session_review.py kept a hardcoded copy of the OLD pattern
(`^SESSION\d{3}$`). Every student finishing a lesson since then got a 502 at
session end. Verified fixed live: fresh session -> turn -> `/session/end` 200.

**To revert:** `git revert d4b417f`.

### BACKEND — `192ef1f` — the unwinnable explanation loop  <- Manjusha's "breaks after some convo"

A scripted 30-turn conversation surfaced it: correct answer, tutor asks "How
did you work it out?", then rejects "I moved the number to the other side by
doing the inverse operation on both sides" **29 consecutive times**. Concrete
wording ("I subtracted 6 from both sides") passes; a child's generic phrasing
loops forever, with no error — the lesson just stops progressing. PARTIAL
explanation turns carry attempt_increment=0, so nothing ever counted or capped
them.

Fix: after two rejected explanations on an already-correct answer, accept the
reasoning and advance. Schema-managed turns untouched. Verified live after
deploy with the exact wording that looped:

```
t1: act=REQUEST_EXPLANATION   "Your value is correct. How did you work it out?"
t2: act=REQUEST_EXPLANATION   "Why was that operation the right one...?"
t3: act=ADVANCE_TO_NEXT_QUESTION  >>> ADVANCED to ALG_1STEP_GP_F02
```

Owed honestly: a unit test through the fake-adapter pipeline (the live retest
above is the current regression evidence). **To revert:** `git revert 192ef1f`.

### FRONTEND — `7117163` — expired login now goes to /login

The screenshot report ("why is it opening this instead of login"): an expired
token fell through accessDecision's mock chain because the persisted
role='student' from yesterday's login was still there — straight into the
lesson, where session start 401'd into a dead-end card. Now a
stored-but-invalid token redirects to /login, and the error card's button
becomes "Log in" instead of a "Try again" that can never work. Given the VM
reboots nightly, this hit anyone who left a tab open overnight.

### BACKEND — `7ae026d` — second /session/end killer: the diagnostic

Reproduced live seconds after a real user hit it: the review builder refused
to run if ANY attempted question lacked a locally-registered correct answer —
and the Student Model's diagnostic questions (Q-T01-D01...) are in no local
registry. So every session that touched the diagnostic — every real student's
— 502'd at the end. The registry exists to keep known answers out of the
review text; an unknown answer is nothing to protect. Verified live:
diagnostic turn -> /session/end -> 200. **Revert:** `git revert 7ae026d`.

### FRONTEND — `d33bcca` — voice consistency through the Cartesia outage

The priority item. With Cartesia hard-down on quota (live right now), the
app used to flip-flop real-voice/robot every 60s in the diagnostic and go
COMPLETELY SILENT in guided practice (a failed audio stream just stopped).

Now: after a provider fails its same-provider retry, the session speaks in
the other product voice — premium Cartesia <-> basic Inworld, never OpenAI,
never silent — for 5 minutes, then tries the real voice again, so topping up
the account restores Skylar automatically. Failed WebSocket audio streams
speak the same words through this chain instead of going mute. Loudly logged:
one console line says exactly what happened.

Verified live post-deploy: Cartesia 502 (quota), Inworld 200 with audio —
the chain has a working target. Also in this commit: the floating "Need
help?" pill sat exactly over the "I'm done" button on /practice at every
viewport width and swallowed its clicks; the action row now clears it.
